# 词条编辑与合并规范

MetaFusion 是一个由社区共同维护的开放元数据平台。具备编辑权限的注册用户参与词条创建、元数据修正与合并。
为了保障全站元数据的准确性、一致性与可检索性，请在编辑时遵循以下规范；写入接口的字段与错误码见
[新建与编辑](/api-edit)。

## 1. 基本编辑原则

- **客观考据**：优先核对官方网站、出版/发行/制作/权利方资料与发行物实物，辅以 MusicBrainz、VGMdb、Bangumi、IMDb 等可核验数据库。
- **来源逐条核实**：每条来源须核实其实际支持的字段；发生冲突、无法核实或事实未知时标注待核并留空，不得猜填。
- **信息完整**：尽量补齐原名、外文名、发行日期、标签、制作团队与封面
- **改动说明（`edit_note`）**：每次提交都要说明修改依据；服务端要求非空
- **来源引用（`sources`）**：至少一条可核验来源，每项为 `{ kind, citation, url }`，`kind` 取
  `url` / `publication` / `self`；缺说明或来源会被 `400 evidence_required` 拒绝

## 2. 命名与多语言规范

### 作品与发行版命名

- **首选原名**：使用作品在原始发行语言中的名称
- **多语言别名**：在 `translations` 的对应语种行补充译名与别名，便于不同输入习惯的检索
- **标点符号**：与官方原始排版保持一致；副标题用空格或冒号分隔

### 创作者命名

- **个人与团体**：使用最广为人知的官方艺名/常用名；一人多艺名时建主实体并在别名中补充
- **多重身份**：创作者实体独立于具体作品，通过关系（如监督、声优、作词、作曲）建立关联，
  不按作品重复创建同一人物

## 3. 实体层级拆分

按平台的固定八类骨架拆分（`agent` / `collection` / `work` / `content_unit` / `expression` /
`release` / `medium` / `track`）：

| 实体 | 对应内容 | 举例 |
|---|---|---|
| **作品（work）** | 抽象创作本体 | 《攻壳机动队》剧场版、《残酷天使的行动纲领》 |
| **内容单元（content_unit）** | 同作品内的稳定目录节点 | 第 1 话、第三章、游戏路线 |
| **表达（expression）** | 某一作品的具体表现，可挂在内容单元下 | 原版立体声母带、导演剪辑版正片、中文译本、2020 重制版 |
| **发行（release）** | 具体出版包，`subjects` 可关联多个作品 | 2003 年发行的初回限定版 CD（品番 KICA-1234） |
| **载体与曲目（medium / track）** | 介质容器与收录位置 | Disc 1 (CD) 的 Track 01；`contents[].expression_id` 指向被收录表达 |

作品形态用标签与动态类型表达，不用 `media_type` 之类的树状分类；季、卷、载体、规格放在对应层级。

## 4. 外部权威标识

为便于自动化识别，实体可关联外部权威 ID（写入 `external_ids`）。键必须已在实例登记的
外部库清单里（见 `GET /api/catalog/external-databases`），常用来源：

> 这一节是可登记的外部 ID 键，不等于可一键导入的来源：导入适配器目前只有 Bangumi 一个，
> 以 `GET /api/importer/sources` 为准（见 [新建与编辑](/api-edit) 的「外部导入」）。

- **音乐**：MusicBrainz、VGMdb、ISRC
- **动画 / 影视**：Bangumi、AniList、IMDb、TMDb
- **图书 / 视觉小说**：ISBNdb（`isbndb`）、VNDB（`vndb`）、豆瓣读书（`douban_book`）

## 5. 消歧与重复合并

### 何时需要合并

发现同一实体被重复创建时（例如不同译名建了两个《EVA》条目）：

1. **确认同一性**：比对官方编号、创作者与发行日期
2. **选择保留主体**：选创建较早、元数据较完善或关联资源较多的那个（合并目标）
3. **发起合并**：由持 `catalog.lifecycle.manage` 权限的成员在管理台或经
   `POST /api/catalog/entities/:id/lifecycle` 执行；普通编辑者请在社区提出合并请求
4. **两种动作**：请求体带 `target_id` 为合并，不带为退役

### 合并后的数据

- 目标必须与被合并实体同 kind、同归属（作品 / 发行版 / 载体 / 父节点一致）且已发布，
  否则服务端拒绝（`invalid_merge_target`）
- 指向原实体的关系与结构引用会被改写为指向保留实体
- 原实体状态置 `merged` 并写入 `redirect_id`，旧链接用
  `GET /api/catalog/entities/:id/resolve` 跟随到保留实体
- 两个实体各自的修订历史都保留，不会合并成一份

::: warning 注意
当前没有「撤销合并」端点；合并前务必确认。
:::

## 6. 违规与争议处理

- **恶意破坏与灌水**：严禁提交虚假信息、清空元数据或批量灌垃圾内容，违规账号会被限制编辑权限
- **观点与分类争议**：题材、分类或标签有争议时，在社区板块发帖讨论，由社区与站务协助判定
- **误操作回滚**：实体没有「一键回滚到某个版本」的端点；请用
  `GET /api/catalog/entities/:id/revisions` 对比历史快照，再按历史内容重新写入正确版本。
- 动态定义的版本可以回滚，见 [新建与编辑](/api-edit)
